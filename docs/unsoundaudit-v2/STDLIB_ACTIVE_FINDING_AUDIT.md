# Standard-Library Active-Finding Audit

## Contract and scope

This is the closed validation inventory for the v5 standard-library active population. The committed population contains 37 active scanner findings grouped into 23 exact families; neither count is a current-bug count.

The table was frozen from the committed v5 family reports and the committed v4 `family_reviews.json`. The **source evidence / proof status** column records the evidence at the current validation boundary. At the Task 1 contract-freeze boundary no family was `confirmed_safe` or `confirmed_ub`; later task sections and the affected rows record evidence-driven disposition changes.

Disposition meanings:

- `confirmed_safe`: a complete source/contract proof closes the family.
- `likely_safe`: existing source evidence suggests a false positive, but the proof is incomplete.
- `poc_required`: static evidence leaves a safe-call soundness question that needs a targeted PoC.
- `confirmed_ub`: a safe public call chain has reproducible UB evidence.
- `inconclusive`: available evidence cannot support another disposition.

The pinned `alloc::str::{join, concat}` family is `confirmed_ub` for rustc commit `1bc403daadbebb553ccc211a0a8eebb73989665f`. A dependency-free application containing no `unsafe` reaches Miri-reported UB through the safe `join` and `concat` APIs when an entirely safe `Borrow<str>` implementation returns a longer string on its second call. Current Rust is not an unreported candidate: stable 1.97.1 contains the upstream repair, current-nightly Miri does not reproduce UB in either profile, and the same root cause was already fixed by rust-lang/rust PRs [#155708](https://github.com/rust-lang/rust/pull/155708) and [#155858](https://github.com/rust-lang/rust/pull/155858) for the 1.97.0 milestone.

## Task 6 proof closure for the remaining active population

The following proofs bind only the exact active sink, safe public roots, and pinned rustc commit `1bc403daadbebb553ccc211a0a8eebb73989665f`. They establish that the 22 remaining families (35 findings) are false positives at that source revision; they are not a claim that every behavior of the surrounding APIs has been verified. ### Clamped `array::IntoIter` ranges

Families `29430f8d...2a36`, `5809e772...a441`, `d8f93399...339f`, and `3457eb7b...ea13` share the private invariant `0 <= alive.start <= alive.end <= N`, with exactly `data[alive]` initialized (`library/core/src/array/iter.rs:14-35`). Let the old live range be `[s,e)` and `L=e-s`.

- `take_prefix(n)` chooses `m=s+n` when `n<=L`, otherwise `m=e`; therefore `s<=m<=e`, the addition cannot overflow, and the returned `[s,m)` is an initialized subset. It stores `alive.start=m` before `drop_in_place` at `array/iter.rs:281-294`.
- `take_suffix(n)` symmetrically chooses `m=e-n` when `n<=L`, otherwise `m=s`; `[m,e)` is valid and it stores `alive.end=m` before the sink at `array/iter.rs:336-349`.
- In both directions `range.len()=min(n,L)<=n`, so `n-range.len()` cannot underflow. If an element destructor panics, the owning iterator already excludes the selected range, preventing a second drop; slice drop glue owns the remaining selected elements during unwind. The char case-mapping roots only forward `n` into the same implementation.

Thus both unchecked range accesses use the exact initialized array and remain valid on normal and unwind paths.

### `VecDeque::truncate` branch and unwind proof

Families `9a5d7fe1...02be`, `bf97c840...85e3`, `2b3ed48b...2e74`, and `6c9651ab...df39` reach `library/alloc/src/collections/vec_deque/mod.rs:1165/1170`. Let the logical length before truncation be `L`, and let `as_mut_slices` return disjoint logical slices of lengths `F` and `B`, where `F+B=L`. The early return proves the sinks are reached only for requested `l<L`.

- If `l>F`, `begin=l-F` satisfies `0<begin<B`, so `back[begin..]` is valid and the retained length is `F+begin=l`.
- If `l<=F`, `front[l..]` is valid and, together with all of `back`, is exactly the disjoint removed suffix.

Both branches store `self.len=l` before running any destructor. In the second branch a `Dropper` for `back` is installed before dropping the front suffix, so a destructor panic still drops the other removed region while the deque itself exposes only the retained elements. The indirect `resize`, `resize_with`, and `IntoIter::advance_back_by` roots branch before calling `truncate`, ensuring the requested length is at most the old logical length; only a strict decrease reaches these sinks. Their growth and generator paths do not reach the sinks. In `advance_back_by`, the `old<n` branch clears first and computes `n-old` only afterward, while the other branch computes the guarded `old-n` retained length.

### `get_many_mut` fixed-array indices and alias proof

Families `c0fa3358...245f` and `c48ccaae...f27a` track the loop variable `i`, not the caller-provided element index. At `library/core/src/slice/mod.rs:4504-4505`, `for i in 0..N` directly proves both `indices[i]` and output-array slot `i` are in bounds for arrays of length `N`. Before entering the unsafe helper, `get_many_check_valid` separately checks every caller index against the same slice length and compares it with every earlier index. Normal continuation therefore gives in-bounds, pairwise-distinct element indices; no callback or mutation occurs between that check and construction of the `N` disjoint mutable references. The `N=0` case is vacuous. The earlier audit rationale was incomplete because it did not identify the reported subject as the fixed-array loop index.

### `OsStr::slice_encoded_bytes` normalized range

Family `4261bfac...8fc` uses `slice::range(range, ..encoded_bytes.len())` before `library/std/src/ffi/os_str.rs:1052`. Excluded starts and included ends use `checked_add`; overflow, `start>end`, or `end>len` panics before the sink (`library/core/src/slice/index.rs:863-893`). A returned range therefore satisfies `0<=start<=end<=L` for the exact immutable `encoded_bytes` slice. User `RangeBounds` methods and both platform boundary checks also run before the unchecked access; an unwind never reaches it. ### `Split` and `RSplit` returned-index contract

### `Cursor<Vec<u8>>` capacity and initialization

Family `caabff54...441a` reaches `library/std/src/io/cursor.rs:474`. Let `P` be the checked `usize` cursor position, `L<=C` the vector length/capacity, `B` the total input length, and `D=P.saturating_add(B)`. If `D>C`, normal return from `Vec::reserve(D-L)` guarantees the same vector now has `C>=D`; otherwise that relation already holds. If the mathematical sum saturates, a non-ZST `Vec<u8>` cannot have `usize::MAX` capacity, so reserve terminates with capacity failure or allocation failure before the sink. Thus every continuing path has `P+B<=C`.

When `P>L`, `diff=P-L<=C-L=spare_capacity_mut().len()`, proving the unchecked padding range. The fill initializes `L..P` before `set_len(P)`. Single and vectored writes then copy only prefixes whose cumulative lengths are at most `B`, and set the length only after initialization. Allocator normal return is an unsafe-trait contract guaranteeing valid storage; error, panic, or abort does not continue to the sink, and no allocator or user callback runs after the spare slice is acquired.
